Reproducing AutoFEA: When an LLM Writes the Finite Element Model

By Mayank Deshpande · 23 Oct 2026

Ask a language model how far a steel beam bends and it will give you a confident number from memory. AutoFEA (Hou et al., AAAI 2025) has a better idea: make the model write a finite element model, a CalculiX .inp deck, solve it, and answer from the solver's output. A graph neural network picks the example code the model learns from, step by step.

I rebuilt it from the paper and the authors' notebook, with Gemini in place of GPT-4o. Every default follows the paper; where the paper is silent, the notebook decides, and everything I added is opt-in. The paper reports a 90.2 % success rate. My first converged run scored 10 % (10 test projects, split 0, Gemini 3.5 Flash, $4.92). This post is about why.

A reproduction, not a rebuttal
These are early numbers from a proof of concept: one split, ten projects, one model. They don't show the method can't work. They show where my faithful-as-I-could-make-it version breaks, and where the paper leaves room for different readings.

1. Plan

Find the training description most similar to the new one (embedding cosine), and use it and its plan as a few-shot example. The LLM plans each step: start card, keywords, description.

Known steps

The structure and mesh steps are given, not generated, as in the paper. In the dataset that prefix holds 62 % of a deck's lines, node numbering included. The LLM writes the physics around it.

2. Retrieve

A GCN-Transformer walks a graph of 5,000+ benchmark steps. Starting from the known steps, it picks one example per planned step, and each pick extends the path.

3–4. Generate, review, solve

Each step is written from its example and the code so far. The LLM reviews the integrated deck against the request, CalculiX solves it once, and the answer comes from the results.

The paper compares five frameworks: direct (complete the deck in one call), rag (plus the most similar training deck), plan, rag_plan (plan plus per-step embedding retrieval) and autofea. Success is the paper's own test: the deck runs, and its .dat output matches the original deck's to a relative 1e-4 or absolute 1e-6.

What the Paper Leaves Open

The authors released the dataset and one notebook. The notebook covers plan generation, step segmentation and the .dat comparison. It has no retrieval model, pipeline or evaluation code, so everything else had to be reconstructed.

Steps and keywords: ported exactly

The notebook's segmentation is ported line for line, and it reproduces the start card, keywords and code of all 528 released .plan files. A step's keywords turn out to be its card and option names, which matters later.

528 projects, not 512

The paper reports 512 projects and 4,792 steps. The released dataset has 528 projects and 5,659 steps, and no list of the paper's 512 exists, so the PoC uses all of them, in three seeded 90/10 splits (475 train, 53 test each).

Which steps are "known"?

The paper treats "the initial steps … that describe the structure and mesh" as given. The PoC makes that precise: the steps right after the heading whose start card is a structure or mesh card (*NODE, *ELEMENT, *NSET and so on). 520 of 528 projects have such a prefix.

References from the same solver build

The success test is strict near zero. Against the .dat.ref files shipped with CalculiX, only 285 of 421 original decks pass it on ccx 2.23, because round-off between solver builds exceeds 1e-6. So, as the paper describes, the reference is the original deck run on the same local ccx. 497 of 528 original decks run.

Layer sizes, epochs, negatives

The paper fixes the model's order (GCN → path attention → classification) and the attention form, but not sizes, epochs or checkpoint rules. The PoC uses a 2-layer GCN (768 → 256 → 256), an MLP classifier, Adam at 1e-3, 16 negatives per target and a fixed 30 epochs with no validation selection: about 13 minutes per split on a CPU.

The paper's retriever links two steps when they share at least one keyword, and trains with easy negatives: nodes that share no keyword with the target. Implemented literally, it picks an example with the planned step's start card less than half the time. Plain description cosine almost always does. This is the leak-free test, where the query carries only the step description, as a plan would:

With 16 negatives per positive, a loss of 0.224 means the model is predicting the base rate and nothing else. Two causes follow from the recipe:

  • The objective doesn't match the task. Training separates the target from nodes that share no keyword with it. At inference the competitors that matter are the ones that do, such as every *MATERIAL step for a material target, and the classifier never sees them as negatives. It learns "plausible for this kind of step", not "this step".
  • The graph is dense. About 20 % of all step pairs are linked (2.57 M edges over 5,105 nodes), so each GCN output averages roughly a thousand neighbours. Nodes in one keyword cluster end up nearly identical: mean pairwise cosine 0.71 after the GCN, against 0.82 for the raw embeddings.
A trap in the obvious metric
Because a step's keywords are its card and option names, a query that includes the true keywords already contains most of the code signature the metric compares. Keyword overlap wins that test almost by definition. Only leak-free or end-to-end numbers say what a learned retriever adds.

The opt-in fix, train --hard-negatives N, adds negatives with the target's own start card, which are exactly the competitors the argmax faces. It isn't in the paper, and it isn't evaluated yet.

The Case Study Doesn't Add Up

The paper's showcase (Figure 4) is an 8×1×1 cantilever, E = 210 000 MPa, ν = 0.3, kinematic hardening from a yield stress of 800 MPa, "a concentrated load of magnitude 10.0" at the free end, and a nonlinear geometric step. The bare LLM answers 0.0975, which the paper calls a hallucination from assuming linear behaviour. AutoFEA answers 0.8738.

But for those inputs, linear beam theory gives PL³/(3EI) = 0.0975 exactly. The largest bending moment, 80, is below the first-yield moment of about 133, so the beam never yields and plasticity never switches on. The beam matches dataset project beampd in every stated property, so I solved it in CalculiX with five readings of the unstated load:

Bare Gemini checked for yielding, added a shear correction and landed within 1 % of the reference. For the prompt as published, the "hallucinated" answer is essentially right; the 0.8738 must depend on inputs the paper doesn't state. Where the Decks Broke

A missing STORAGE=YES

7 of the 15 failed runs stop with "cannot open eigenvalue file". The generated *FREQUENCY steps omit STORAGE=YES, so the modal-dynamics step after them has no eigenmodes to read.

rag copies siblings

The sample has four beamdy* projects, near-duplicate decks with siblings in the training split. Three of rag's four successes are those siblings. Whole-deck retrieval thrives on a dataset like that.

One wrong token

The smoke run wrote *EL PRINT S,SF,EVOL. SF is invalid there, and the original prints EVOL separately with TOTALS=YES. Its *STEP example came from the coupling1 hub.

AutoFEA writes result tables as often as rag (60 % of runs) but rarely matches the reference values. The decks are well-formed and numerically wrong, which fits wrong examples better than syntax trouble.

What I Built Around It

The pipeline is TypeScript on pi-ai, so Gemini runs through Google AI Studio or Vertex AI with one setting. The retriever is PyTorch behind FastAPI. Every stage emits typed events that a Fastify server streams over SSE to a local React UI. You watch the plan, the retrieved examples, each generated step, the review and the solver run arrive live, then open the results in a three.js viewer that reads CalculiX's .frd output.

The extensions stay opt-in and labelled "not in the paper": a repair agent (pi-agent-core, with read_deck, replace_lines and run_calculix tools, at most 5 solver runs), an agent mode where one pi-coding-agent session plans, writes, runs and fixes, extra retrievers and metrics, and a fully specified suite of five problems checked against hand calculations. The tests run against a zero-cost scripted LLM, which is how they caught a scoping bug in the LLM wrapper.
