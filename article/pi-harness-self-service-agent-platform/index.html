pi harness: A Self-Service Platform for Document-Grounded Agents

By Mayank Deshpande · 23 Oct 2026

Every large organisation has the same pile: hundreds of manuals, policies and procedures, plus spreadsheets nobody can find. The usual answer is one bespoke chatbot per source, and that doesn't scale past the third one. pi harness is the opposite bet: one self-service platform where any team can create an agent, upload its documents, write its instructions, publish it, and chat with it, with every claim cited back to a page.

Under the hood each conversation is a session of pi, a minimal open-source agent harness with an SDK, running Gemini on Vertex AI. The rest is the platform around it: a Fastify API on Cloud Run, Cloud SQL Postgres for metadata, a Python ingest worker, and a React frontend that streams the agent's work live.

From a Folder of PDFs to a Cited Agent

The whole product is four verbs. No ticket to a platform team, no prompt engineering in a notebook.

1. Create

Name an agent; you become its owner. Grant user, editor or owner roles to people or Google Groups.

2. Upload

Drop PDFs, Office files and spreadsheets. A worker turns them into page-anchored Markdown and queryable Parquet in the background.

3. Instruct

Write the instructions, attach skills (Agent-Skills-compatible SKILL.md files) and set guardrails: blocked topics and a tool-call budget.

4. Publish & chat

Publishing freezes an immutable version. Every chat is pinned to one, and editors can test the draft side by side first.

What Happens Behind One Message

The API is stateless on purpose: any Cloud Run instance can serve any turn, and none of them keeps a conversation in memory.

Check & lease

The caller must own the session and still hold a role on the agent. A turn lease in Postgres guarantees one turn at a time per session, across every instance.

Build a pi session

The transcript comes from the bucket, and a local cache provides the session's pinned published version. pi gets our system prompt, the agent's skills, the guardrails extension and read-only tools only.

Stream & persist

pi's internal events are mapped to a stable schema and streamed as SSE. Afterwards the transcript goes back to the bucket, usage and audit rows go to Postgres, and the lease is released.

The frontend never sees pi's own event types, only this stable ChatEvent union, so upgrading pi can't break the UI:

The Agent's Toolbox

Retrieval is hybrid. Instead of stuffing the top-k chunks into a prompt and hoping, the agent navigates its documents with tools, the way a person would: skim the index, search, open the right pages, then answer.

list_documents

The manifest: every document's title, summary, table of contents, and every table with its columns. Usually the agent's first move.

search_documents

Semantic search through Vertex AI RAG Engine, mapped back to the page each chunk came from. With no corpus (local dev) it falls back to BM25 keyword search over pages.

read_document

Reads a bounded page range and returns it with [docId:page] anchors, which is where every citation in an answer comes from.

query_table

One DuckDB SELECT over the agent's Parquet tables, inside a locked-down sandbox. Spreadsheets become queryable instead of being pasted into the prompt.

pi's built-in read, grep, find and ls are available too, confined to the agent's workspace. bash, edit and write are never enabled.

Guardrails You Can Reason About

An agent anyone can create has to be safe by construction, not by a polite system prompt.

A SQL sandbox that only says SELECT

query_table doesn't trust a regex. It asks DuckDB's own parser (json_serialize_sql) and rejects anything that isn't a single SELECT: no DDL, DML, COPY, ATTACH, PRAGMA or SET. Table functions like read_csv and unknown tables are refused. The query runs with external access off, allowed_directories limited to the tables it touches and the configuration locked, under a 200-row cap and a 20-second timeout.

The model never learns where it lives

pi normally tells the model its absolute working directory and skill locations. The guardrails extension rewrites both to workspace-relative paths, so server paths never reach the model and can't be echoed back. The SSE mapper strips the same prefix from tool arguments before they reach the browser.

Blocked topics and a tool budget

Editors list topics the agent must not discuss. A matching message is handled before the model runs and the browser gets a blocked event, exactly as in the demo above. A per-turn tool-call budget stops runaway loops, and any file tool that reaches outside the workspace is denied.

Access control that doesn't leak existence

Roles go user < editor < owner, granted to people or Google Groups (nested groups included), behind Identity-Aware Proxy SSO. A caller with no role gets 404, not 403, so agent IDs can't be probed. Lose your role mid-conversation and the next turn is refused.

Turning Files Into Something an Agent Can Cite

Uploads go straight to Cloud Storage through a signed URL. A finalize event wakes the Python worker on Cloud Run, which writes everything into the agent's draft workspace and moves the document from parsing to ready (or failed).

Each document also gets a Gemini-written summary and table of contents in the agent's manifest.json, which is what list_documents serves. The manifest is updated with GCS generation preconditions, so two uploads finishing at once can't overwrite each other's entries.

Ask for a Dashboard, Get One

On an agent with spreadsheets, "show me delays by month" makes the model write a dashboard spec, not HTML. The server runs each dataset's SQL through the same DuckDB sandbox and renders one self-contained file with ECharts inlined. A conversation has exactly one dashboard: later requests become new tabs inside it, never a pile of loose files.

It's framed from a separate origin with sandbox="allow-scripts" and connect-src 'none', so even generated JavaScript can't phone home. The dashboard follows its agent's ACL: lose access to the agent and you lose the dashboard.

Small Things I Learned Building It

Vertex auth on Cloud Run needs a white lie

pi only reports the google-vertex provider as available when an Application Default Credentials file exists, and Cloud Run doesn't have one. The fix: register the placeholder key <authenticated>. pi's Vertex client treats it as "no key" and falls through to ADC from the metadata server. No secrets anywhere; every service authenticates as its service account.

Postgres tests with no Postgres

Database tests run against PGlite, Postgres compiled to WebAssembly and running in-process, so npm test needs no server and no Docker. The same trick powers npm run dev:db for local development.

End-to-end tests with a scripted model

The e2e server is the real API, database, bucket, worker and workspace cache, with pi's faux model in place of Gemini. It searches, reads the best page and answers with a citation, which is the same flow the demo above replays. The whole UI, citations included, can be exercised without a model key.
